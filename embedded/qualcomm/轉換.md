Part 1：Host 端（x86 Linux PC）模型轉換
Step 1：安裝並設定 QAIRT SDK
``` bash
# 下載並解壓縮 QAIRT SDK 後，設定環境變數
export QNN_SDK_ROOT=/opt/qairt/2.42.0.251225
source $QNN_SDK_ROOT/bin/envsetup.sh
```

Step 2：準備並檢查 ONNX 模型
``` bash
python3 -m onnxsim model.onnx model_sim.onnx
```

Step 3：ONNX → 浮點 DLC
``` bash
qairt-converter --input_network /home/eray/repo/model_hub/det/yolov8n/yolov8_640X640/yolov8n_sim.onnx --output_path /home/eray/repo/model_hub/det/yolov8n/yolov8_640X640/qualcomm/yolov8n_sim.dlc
```
- -d `'<輸入tensor名稱>' <shape>`：明確指定輸入維度，避免 converter 猜錯。
- 輸出的 model_fp.dlc 是框架中立格式，此時精度、資料型別跟原始 ONNX 一致（浮點）。這個檔案已經可以在 CPU/GPU backend 上跑，但還不能用在 HTP（Hexagon NPU）上。

Step 5：DLC 量化（INT8）
``` bash
qairt-quantizer --input_dlc /home/eray/repo/model_hub/det/yolov8n/yolov8_640X640/qualcomm/yolov8n_sim.dlc --input_list /media/storage/media_data/calibration_coco_data/bin_coco_t/file_list.txt --output_dlc /home/eray/repo/model_hub/det/yolov8n/yolov8_640X640/qualcomm/yolov8n_sim_quant.dlc --act_bitwidth 8
```
- --input_list：指向剛剛的 calib_list.txt，工具會逐一跑推論收集每層 activation 的數值範圍，計算量化 scale/offset。
- --act_bitwidth / --weight_bw：分別控制 activation 與權重的量化位元數，8 是 HTP 上最常見、效能最好的設定；精度要求高的層可用 --quantization_overrides 個別排除。
Step 6：建立 HTP 後端設定檔
這一步是針對 IQ9 硬體架構做編譯前的設定，需要兩個 JSON：

config_backend.json：
``` json
{
    "graphs": [
        { "graph_names": ["model"], "vtcm_mb": 0 }
    ],
    "devices": [
        { "dsp_arch": "v75", "soc_id": 60 }
    ]
}
```
config_file.json：
```json
{
    "backend_extensions": {
        "shared_library_path": "libQnnHtpNetRunExtensions.so",
        "config_file_path": "config_backend.json"
    }
}
```

⚠️ dsp_arch / soc_id 要對應到 IQ9 的實際型號（IQ9 系列有多個子型號，Hexagon 版本可能是 v73 或 v75）。這兩個值 Qualcomm 沒有公開統一對照表，最準確的做法是在目標裝置上執行：
``` bash
qnn-platform-validator --backend libQnnHtp.so
```

或查閱該 IQ9 型號隨附的 BSP / QAIRT 文件裡的 htp_backend 章節，裡面會列出正確數值。

Step 7：DLC → Context-Binary
``` bash
qnn-context-binary-generator --model qnn-context-binary-generator --model /opt/qcom/qairt/lib/x86_64-linux-clang/libQnnModelDlc.so --backend /opt/qcom/qairt/lib/x86_64-linux-clang/libQnnHtp.so --dlc_path /home/eray/repo/model_hub/det/yolov8n/yolov8_640X640/qualcomm/yolov8n_sim_quant.dlc --output_dir /home/eray/repo/model_hub/det/yolov8n/yolov8_640X640/qualcomm/ --binary_file yolov8n_sim_quant_qnn --config_file /home/eray/repo/model_hub/det/yolov8n/yolov8_640X640/qualcomm/config_file.json
```
邏輯說明：這一步是把量化後的 DLC graph 針對 IQ9 的 Hexagon 架構做提前編譯（AOT），產生的 output/model_ctx.bin 已經是硬體可以直接載入執行的指令序列，不用在裝置上重新編譯 graph，可以大幅縮短模型初始化時間、降低記憶體用量。

Part 2：裝置端（IQ9 板子）部署與推論
``` bash
scp -r /opt/qcom/qairt/lib/aarch64-oe-linux-gcc11.2/ /home/eray/repo/model_hub/det/yolov8n/yolov8_640X640/qualcomm/ /opt/qcom/qairt/bin/aarch64-oe-linux-gcc11.2/ /opt/qcom/qairt/lib/hexagon-v73/ root@192.168.33.128:/root/qnn
```

這裡的邏輯：QNN 的 HTP backend 是分層架構——libQnnHtp.so 是 ARM 側的介面層，libQnnHtpV75Stub.so 是跟 DSP 溝通的 stub，libQnnHtpV75Skel.so 才是真正跑在 Hexagon DSP 上的執行檔（Skel = Skeleton，DSP 端的實作）。三者版本號（V75）必須跟你在 Step 6 設定的 dsp_arch 一致。

Step 2：準備測試輸入並執行推論
``` bash
# 裝置上執行
./qnn-net-run \
  --backend ./libQnnHtp.so \
  --retrieve_context ./model_ctx.bin \
  --input_list ./test_list.txt \
  --output_dir output_bin
--retrieve_context：直接載入預編譯好的 context binary，跳過 graph 建構階段。
```
輸出結果會以 raw binary 存在 output_bin/，需要自己寫腳本 parse 回可讀格式（例如根據輸出 tensor shape 用 numpy fromfile 讀回）。
